# How it works

- **Login.** Instagram's own login page runs in a web view, and its cookies stay on the phone in a WebKit store ([Session.swift](../Unreeled/App/Session.swift)). Once the session cookie appears, the app switches to the native screens.
- **Requests.** [WebRequests.swift](../Unreeled/API/WebRequests.swift) sends every request the way Safari sends a `fetch()` from a blank page on www.instagram.com: WebKit's user agent and the same headers (`Accept`, `Origin`, `Referer`, `Sec-Fetch-*`, `Priority`), with the website's cookies. The cookies stay in WebKit's store on the phone: the app reads them from there for each request and writes back what responses set, so the login page and the website's screens share them. On iOS, WebKit loads pages through the same system networking that URLSession uses; sent both ways to a local echo server, the two carried the same set of headers, and a request to i.instagram.com is preceded by the same preflight (`OPTIONS`) a browser sends. WebKit's user agent and touch points are asked of WebKit once per version of iOS (`BrowserIdentity`).
- **A weak connection.** Until 13 November 2026, requests ran as `fetch()` inside a hidden web view; a dropped connection there came back as a bare "A JavaScript exception occurred", with nothing tried again. Now a failed request says why (no connection, or a connection that dropped or stalled for 15 seconds). Reading is tried three times, a moment apart, but not without any connection: screens then show what they saved and load again when [Connectivity.swift](../Unreeled/App/Connectivity.swift) sees the phone back online. Something to send waits up to a minute for a connection, and is tried again only when it certainly never left the phone (no connection, no host, no TLS), so nothing goes twice. A request, once started, finishes even if its screen has gone, as a page's fetch did, unless the app abandons it (a notification reply out of time). A Debug build can play a poor connection: `-flakyNetwork 0.5` fails half the requests (a change fails before it leaves the phone), `-slowNetwork 3` delays each, `-offlineFor 20` acts as if offline for the first 20 seconds, and `-cookieLog YES` logs which cookies each request carries, by name and length only.
- **GraphQL.** Nearly everything the website loads comes from GraphQL queries that it sends by ID. [Queries.json](../Unreeled/API/Queries.json) lists the ones the app uses: the ID, the endpoint, and the feature flags each query expects. The app sends them with the same parameters and headers as the website. It reads the session tokens they need (`fb_dtsg`, `lsd`) from a website page's HTML and keeps them in the Keychain, only when the page was a logged-in one. [Endpoints.swift](../Unreeled/API/Endpoints.swift) has the variables for each screen. Long lists can arrive in parts, one JSON document a line; the app splits a response at line feeds only, since other line breaks (U+2028, U+2029) can sit unescaped inside someone's message.
- **Query updates.** [QueryUpdates.swift](../Unreeled/API/QueryUpdates.swift) downloads the project's current Queries.json from `https://unreeled.app/queries.json`, or from this repository on GitHub if that fails. It checks at launch at most every 6 hours, and right after a query fails at most every 10 minutes; after a failure, a query whose entry changed is tried once more. Only entries for queries the app already sends are taken, and only if they look like Instagram's (a numeric ID, one of the two GraphQL endpoints, `__relay_internal__pv__` flags). A list taken by an earlier version of the app is set aside when the app updates. About shows whether the app runs on its own list or a newer one.
- **Comet GET.** A few website calls, such as Direct search, are GETs that need the page's `async_get_token` and the website's full set of parameters. `cometGET` in InstagramAPI.swift sends them the way the website's `cometAsyncFetch` does.
- **Home** asks for the website's Following feed (`instagram.com/?variant=following`). The default ranked feed turned out to be mostly reels, Explore suggestions and ads.
- **Models.** Responses decode into [Models.swift](../Unreeled/API/Models.swift), where nearly every field is optional, so a field Instagram drops doesn't break a screen.
- **Screens** are in [Views](../Unreeled/Views). Images are kept decoded in memory and as files on the phone (`ImageCache` and `ImageFiles`), both keyed by the picture's path on the CDN and its size (`stp`), never by the full link: Instagram signs each link anew in every response. Pictures are decoded no larger than the screen, with ImageIO reading them down to that size as it decodes, so a file that claims an enormous size takes no more memory than the screen needs. One that doesn't decode, even freshly downloaded, isn't asked for again until the next launch.
- **Conversations** look for new messages every 15 seconds, and mark what's new read, only while they're on screen: in the open tab, with nothing opened over them and the app in front. One left open in a tab you switched away from (by tapping a notification about something else) waits until you're back, then catches up. A message its sender unsent disappears at the next look: it's missing from Instagram's latest messages, though newer than the oldest of them.
- **Links someone else chose** (a link shared in a message, a profile's website) open only when they're web links, `http` or `https`; any other kind (another app's link, a phone number) does nothing at a tap, and the profile shows no website. Instagram's own pages open in a web screen, other sites in Safari.
- **Web screens** ([WebScreen.swift](../Unreeled/Web/WebScreen.swift)) inject [Filter.js](../Unreeled/Web/Filter.js) with [Rules.json](../Unreeled/Web/Rules.json). They always start on www.instagram.com: a path that would lead to another site, or to no page, opens the home page. Links to other sites open in Safari, and e-mail, phone and message links in their apps, only right after a tap (Instagram passes outside links through a page of its own, which then moves on to them): a page never sends you out of the app on its own. Links that would open Instagram's app are ignored, and so is any page without an address except a blank one.

## Endpoints, and how each was tested

The tests below were made when requests ran inside the hidden web view. With the native requests, the reading ones were tried again on 13 November 2026 (feed, stories and the viewer, profiles, Direct's inbox and search), also with a poor connection played by a Debug build; sending, uploads and story posts haven't been tried with them yet.

**Messages** use the website's own Direct queries (`PolarisDirectInboxMobileQuery`, `IGDThreadDetailQuery`, `IGDMessageListOffMsysQuery`) and mutations (`IGDirectTextSendMutation`, `useIGDMarkThreadAsReadMutation`), with the variables the website sends. Tested: a text message sent to a test conversation arrived, and the conversation was marked read.

**Photos and videos in messages** are uploaded the way the website's chat does it: a form post to `/ajax/mercury/upload.php` (the file in `farr`), which returns an attachment ID, then `IGDirectMediaSendMutation` with that ID. Videos, here and for stories, are re-encoded first without what the camera wrote about them, such as where they were filmed; photos are drawn anew, which keeps none of it. Tested: a photo and a 3-second video reached a test conversation, and the video played back from Instagram's copy.

**Voice messages** are sent the way the website's recorder does it: Opus audio in an Ogg file named `audioclip-<time>-<length in ms>.ogg`, uploaded to the same `/ajax/mercury/upload.php` with `voice_clip=true` and a 64-level waveform, then sent with `IGDirectMediaSendMutation`. The app records 48 kHz mono and encodes Opus itself ([OggOpus.swift](../Unreeled/API/OggOpus.swift)). Tested: a 21-second test tone reached a test conversation and played back from Instagram's copy. A Debug build launched with `-testVoiceClip YES` records that tone instead of the microphone.

**Hearts** use the website's `IGDirectReactionSendMutation`: the message's ID, the thread's ID, `reaction_status` created or deleted, and the heart as U+2764 without the emoji style mark, which is how the website's code converts it. Tested: a heart was put on a message and taken off again; Instagram accepted both, and its copy of the conversation showed no heart afterwards.

**Direct search** uses `/api/v1/direct_v2/ranked_recipients/?mode=universal&show_threads=true` through `cometGET`. A person found that way opens by their `interop_messaging_user_fbid`, which `IGDThreadDetailQuery` accepts as the thread ID, as on the website.

**Stories** are posted the way the website's story camera does it. A photo goes to `i.instagram.com/rupload_igphoto/fb_uploader_<upload id>`; a video goes to `rupload_igvideo/story_<upload id>`, followed by its first frame as the cover. What they are travels in `X-Entity-*` and `X-Instagram-Rupload-Params` headers. Then `/api/v1/media/configure_to_story/` publishes it, and `/api/v1/web/create/<id>/delete/` deletes it. Requests to i.instagram.com carry only the headers the website sends there (a page's fetch with a CSRF token or claim is refused by the preflight), after the preflight a browser sends first. Tested: a test photo was posted and deleted. Video stories haven't been tried.

**Story likes** use the website's `usePolarisStoriesV4LikeMutation…` mutations with the item's ID. **Story replies** use `IGDirectStoryShareReplyMutation`, as its current stories viewer sends it (the media ID alone, the reel ID, and the owner as recipient). Tested: a reply reached its recipient, and a like then an unlike both showed when the story was loaded again.

**Activity** uses `PolarisActivityFeedStoriesViewQuery`, which the website loads with the page rather than as a request, so it was found in the website's scripts (see [MAINTAINING.md](MAINTAINING.md)). Follow requests use `/api/v1/friendships/approve/<id>/` and `/ignore/<id>/`, as the website does.

**Likes** use the website's own like and unlike mutations (`usePolarisLikeMediaXIG…Mutation`), copied from a recording of the website. They send the post's `organic_tracking_token`, as the website does. Tested: a like and an unlike both showed when the post was fetched again.
